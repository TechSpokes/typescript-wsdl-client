## Existing seams

`orderedSyntax.ts` retains expanded names, attribute identities, namespace scopes and ordered text/elements; it discards comments, processing instructions and CDATA boundaries. `directStructurePlan.ts`, `matchDirectProjection`, `assessProjectionScalars` and `expandProjectionValue` own currently reversible component projections and their native inverse.

`directCodec.ts` accepts authenticated mapping/operation boundaries and emits native inverse output; a syntax tree is not a receipt. `componentShape.ts` lowers actual peer attributes, `$value` and ordered `{name,value}` entries, leaving correlated particles, wildcard membership and scalar duties to native owners.

Legacy `generateClient.ts` uses configurable input `$attributes` and output SOAP `attributes` bags by default, accepts legacy aliases and promotes response attributes into peer properties. Its `$value` handling does not prove mixed-order preservation; the legacy and component formats are separate contracts.

## Bounded primary-source comparison

These are format comparisons, not dependency recommendations or executed third-party results. The library formats below are conventions; the selection in the next section is a repository decision.

| Format / primary source | Comparable small form | Preservation and inverse | Ergonomics / compatibility / schema cost |
|---|---|---|---|
| Existing component | `{id:"7",$content:[{name,value}]}` | Ordered elements; no mixed text yet | Reuse accepted entries and peer attributes |
| Existing legacy | `$attributes` input; `$value`; named children | Cannot establish interleaving from name-keyed children | Keep configurable bags and existing meanings |
| [JsonML](https://github.com/mckamey/jsonml#mixed-mode-xml) | `["p",{id:"7"},"Hello ",["b","world"],"!"]` | Text/element order is explicit | Compact mixed content; replacing ordinary records adds positional tuple complexity |
| [xml-js non-compact](https://github.com/nashwaan/xml-js#compact-vs-non-compact) | `{type:"text",text:"Hello "}` among element records | Explicit node kinds preserve alternating order | Clear inverse; redundant element discriminator and larger union than existing entries |
| [Json.NET](https://www.newtonsoft.com/json/help/html/ConvertingJSONandXML.htm) | `{"@id":"7","#text":"Hello "}` plus children | Documents order loss when differently named nodes are grouped | Useful attribute separation; empty-to-null conflicts with nil distinction |
| [Jsonix](https://github.com/highsource/jsonix#jsonix) | Schema mapping assigns properties to attributes/elements | Declarative mappings may be generated from XSD | Supports deriving known facts; importing its format/toolchain is unnecessary |

JsonML's mixed example above illustrates its array convention; xml-js would represent the same paragraph with a `p` element, its `attributes`, and `elements` containing text/`b`/text records. Json.NET's markers illustrate attribute/text placement, not a claim that one `#text` field preserves the paragraph's three positions. Jsonix's purchase-order example demonstrates schema-derived properties; no specific Jsonix mixed mapping is assumed here.

JsonML and xml-js syntax representations can carry lexical qualified names, namespace declaration attributes and `xsi:nil` attributes, but those positions alone do not establish XSD nil/type assessment or expanded identity. Json.NET uses `@` attribute markers and namespace attributes; its documented empty-to-null convention cannot serve as this repository's nil rule. Jsonix's interpretation depends on its declarative mapping, so nil/context behavior must be specified by that mapping rather than inferred from a library label.

The [XML Information Set](https://www.w3.org/TR/xml-infoset/#infoitem.element) supplies vocabulary for expanded identity, ordered children and namespace context, rather than a JSON format. [XSD Structures](https://www.w3.org/TR/xmlschema-1/#cvc-elt) assigns nil and dynamic type duties to element assessment; [wildcards](https://www.w3.org/TR/xmlschema-1/#cvc-wildcard) retain strict/lax/skip semantics. [XSD Datatypes QName](https://www.w3.org/TR/xmlschema-2/#QName) separates expanded value from lexical prefix/context; literal strings do not gain QName semantics.

[fn:xml-to-json](https://www.w3.org/TR/xpath-functions-31/#func-xml-to-json) consumes that specification's XML representation of JSON, rather than arbitrary business XML. The [OpenAPI XML Object](https://spec.openapis.org/oas/v3.1.1.html#xml-object) annotates names, namespaces, attributes and array wrapping; it does not supply mixed-order or native XSD validation. [Azure APIM](https://learn.microsoft.com/en-us/azure/api-management/xml-to-json-policy) contrasts direct and JavaScript-friendly conversion; this is supplementary vocabulary, not another mode to adopt.

### Alternatives and selection

| Distinction | Alternatives considered | Selected reason |
|---|---|---|
| Mixed text | Bare strings; `{$text:string}`; `{kind:"text",value:string}` | Bare strings are disjoint from existing element objects and add no discriminator |
| Elements | Existing `{name,value}`; new `{kind:"element",name,value}` | Preserve the existing entry exactly |
| Known names/order | Repeat names everywhere; derive from source | Keep existing source-derived ordinary properties |
| Dynamic names | Lexical prefixed keys; expanded entry names | Expanded identity avoids alias and local-name collisions |
| Attributes | All peers; string-keyed bag; expanded-entry bag | Peers stay where accepted; expanded bag handles only dynamic/colliding identities |
| Nil | Always null; `$value:null`; `$nil:true` | Null alone loses attributes; `$nil` does not reinterpret `$value` |
| Context | Drop every prefix; infer colon semantics; retain all open scopes | Unknown application meaning requires original bindings, including rebinding |

The explicit text-record alternative is viable but adds a field and another object shape without resolving a collision: existing element entries are objects and text is always a string. No `kind`, node version, public mode or root envelope is needed. An expanded-name attribute array costs more than a local-key bag, but avoids namespace-key escaping, child collisions and prototype-key assignment.

## Selected component extension

This recommendation is additive only for currently refused component cases. The source-selected projection chooses ordinary record, simple/scalar or ordered content at each location; callers cannot switch shape with a metadata flag, and this document creates no persisted plan format.

| Field / position | Exact meaning | Necessity / source-derived exclusion |
|---|---|---|
| Ordinary properties and arrays | Existing selected component slots | Names/order/grouping remain source-derived |
| Known peer attributes | Existing source-mapped scalar values | Preserve accepted peer shapes and scalar policy |
| `$value` | Existing simple-content text scalar | Never overload as nil or mixed text |
| `$content` | Ordered array of strings or existing `{name:{namespace,local},value}` | Strings are significant mixed text; entries retain variable selection/order |
| `$attributes` | Array of `{name:{namespace,local},value}` | Only dynamic/colliding attributes lacking a unique accepted peer slot |
| `$nil` | Literal `true`, with no content-bearing properties | Nil when attributes or other necessary metadata prevent plain null |
| `$type` | `{namespace:string,local:string}` | Explicit `xsi:type` selection; never a JS class/discriminator |
| `$namespaces` | Object mapping prefix strings, including `""`, to namespace URI strings | Complete effective context at each genuinely untyped element |
| `null` at an element value | Present nil element with no supplied attributes/context/type | Never absence or an empty non-nil element |

`name` and scalar QName objects have exactly `namespace` and `local`, both strings; `local` is an XML NCName. Element entries have exactly `name` and `value`; attribute entries have exactly `name` and `value`. Attribute `value` follows the source scalar descriptor when known, otherwise it is lexical string data in the retained open context; the research bag exercises the latter.

Known colliding declarations use the ordered element channel and the expanded attribute bag where no existing unique peer exists. Do not emit both a peer and a bag entry for one attribute identity. An ordered element entry keeps its accepted expanded name even for known alternatives; an ordinary fixed sequence does not acquire entry names or `$content` merely for uniformity.

### Allowed combinations and rejection

Non-nil values use exactly their source-selected content form: ordinary child properties, `$value`, or `$content`. A mixed/ordered record cannot also contain ordinary child properties or `$value`; known peer attributes, `$attributes`, `$type` and required `$namespaces` may accompany its content. Existing simple-content records may combine their `$value` with accepted peer attributes; new colliding/open attributes use the bag.

Nil uses `null` or an object with `$nil:true` plus attributes, `$type` and required `$namespaces`; no `$value`, `$content` (even empty), or ordinary child property is allowed. `{$nil:true}` is accepted as an attribute-free spelling and canonicalizes to `null`; `$nil:false` is rejected in JSON. On XML input, `xsi:nil="false"` or `"0"` is ordinary non-nil and the marker normalizes away.

Reject unknown metadata, missing entry members, extra entry members, invalid names, duplicate expanded attributes, undeclared peer fields and conflicting channels before returning a reconstructed value. Namespace declarations and `xsi:nil`/`xsi:type` cannot masquerade as application bag attributes. No unknown `$` field becomes an XML child, and no validator silently removes fields, coerces values or mutates inputs.

Legal XML names `__proto__` and `constructor` are ordinary identities, not reserved metadata. Use safe own-property construction for any name-keyed native structures; the prototype preserves these names in expanded entries without assigning them to object prototypes. This does not change current source/bootstrap admission gates or reserve those XML names globally.

### Presence and nil examples

An absent optional child is omitted from its record or ordered sequence. An empty non-nil string element is `""`, an empty ordinary complex value is `{}` where the selected contract permits it, and an empty ordered complex value is `{"$content":[]}`; the source distinguishes these contracts.

```xml
<x xmlns="urn:msg" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" id="7" xsi:nil="true"/>
```

```json
{"id":"7","$nil":true}
```

The fixture's unqualified `id` remains a source-known peer. A separate qualified `a:id` is `{"name":{"namespace":"urn:attr","local":"id"},"value":"qualified"}` inside `$attributes`; the default element namespace never qualifies unprefixed attributes.

In an existing array property, `[null,"",{"$nil":true,"id":"7"}]` denotes three item elements. A wrapper value of `null` denotes one nil wrapper, with no item content; an absent wrapper is omitted. #421 must apply nillability, required/allowed attributes, fixed/default and nil-content constraints at each actual element, never to an array as a surrogate for its wrapper.

### Namespace and contextual scalar rules

A declared QName scalar uses the ADR's expanded `{namespace,local}` value; attributes or simple-content wrappers retain the selected scalar position. `p:T` and `alias:T` are equal only when both resolve to the same namespace; a child rebinding `p` changes the expanded value. A string such as `unbound:T` remains that string, without resolution or guessed semantics.

For genuinely untyped lax/skip subtrees, retain a complete effective namespace map on every element, including inherited bindings, unused bindings and nested rebindings. Retain the default binding when present; `"":""` records a default undeclaration, while `xml` is implicit and omitted canonically. A fresh inverse needs no parent/source XML to interpret the map; it must not change or prune an original binding based on colon heuristics.

Prefixes must be NCNames except the empty default key; reject `xmlns`, invalid `xml` bindings, bindings to the xmlns namespace, and empty URIs for nonempty prefixes. Newly generated prefixes for expanded typed QNames must avoid every retained prefix; no-namespace QName lexical output requires an empty default namespace. A supplied expanded QName incompatible with retained default context is rejected rather than rebinding an unknown application's context.

`$type` records explicit expanded `xsi:type` identity, including an explicitly supplied declared type; it does not prove that type exists or is a permitted derivation. #409/#422 must preserve scalar context and lexical witnesses and perform native dynamic-type duties before admitting this currently refused capability. The prototype resolves QName meaning through the existing `resolveLexicalQName`; an unbound typed QName failure is a native scalar duty, not evidence that all colon strings are malformed JSON.

### Construction and normalization

Forward construction starts with the selected source projection and existing scalar assessment. Keep ordinary records, arrays, Boolean values, int32 numbers, precision-sensitive decimal/integer strings and existing `$value` unchanged; never convert exact scalars through JavaScript `Number`. Source-known uniquely inferable grouping remains reconstructed by the existing projection.

For mixed/variable/open content, visit ordered syntax, append text strings and existing element entries, and preserve significant spaces, nesting and multiplicity. Extract nil and type into their metadata positions, put uniquely mapped known attributes in peers, and put remaining permitted attributes in the expanded bag. Retain scopes only at source-selected genuinely untyped locations; a scalar/known record must reject unsolicited `$namespaces`.

The fresh inverse reads only JSON plus the selected source contract, reconstructs names and fixed sequence from that contract, and walks `$content` for actual order. It reconstructs bag attribute identities, nil and typed-QName namespace bindings without reading the original XML. It then hands the fresh native value to the existing scalar/particle/codec owners; no checked failure is routed through legacy conversion.

Canonical normalization coalesces adjacent text strings, removes zero-length text entries, preserves every significant space, sorts attribute entries by expanded identity, and ignores attribute order. Empty text and CDATA segmentation, comments, processing instructions, prefix aliases, entity spellings, nil false markers and original bytes are outside the adopted equivalence. Unknown lexical application strings and retained bindings remain unchanged.

Schema-defined default/fixed augmentation remains at native assessment; absent required elements are never invented. Lexical-sensitive facets still require a retained admitted witness or justified shared normalization. Invisible group history and empty realizations follow ADR-003's existing canonical representative, not new JSON group tags.

## Concrete mixed and fresh inverse evidence

```xml
<p xmlns="urn:msg" id="7">Hello <b>world</b>!</p>
```

```json
{"id":"7","$content":["Hello ",{"name":{"namespace":"urn:msg","local":"b"},"value":"world"},"!"]}
```

The hand-authored [mixed JSON](../../test/research/xml-json-mapping/mixed.json) inverse reconstructs root `{urn:msg}p`, unqualified attribute `id=7`, and content `["Hello ", {urn:msg}b("world"), "!"]`. The forward path additionally serializes to JSON text and parses fresh JSON before the inverse; neither path consults cached XML.

The independent variable-order JSON `{"$content":[{"name":{"namespace":"urn:msg","local":"a"},"value":"1"},"  ",{"name":{"namespace":"urn:msg","local":"b"},"value":"2"},{"name":{"namespace":"urn:msg","local":"a"},"value":"3"}]}` reconstructs `a,spaces,b,a`, while the existing native fixed-sequence control reconstructs ordinary record fields in source order. The [open XML](../../test/research/xml-json-mapping/open.xml) and independently authored [open JSON](../../test/research/xml-json-mapping/open.json) add namespace/attribute collisions, nested rebinding, literal colon strings, `__proto__` and `constructor`.

The [tests](../../test/research/xml-json-mapping/mapping.test.ts) compare independently specified expanded names, attributes, ordered text, nil and scope maps, ignoring source positions/digests. Separate hand inputs cover nil items/wrapper, expanded QName and dynamic type, while existing native projection/inverse calls cover exact decimal strings, fixed records, repetition, typed peer attributes, Boolean/int32 and simple `$value` controls.

The [prototype](../../test/research/xml-json-mapping/mapping.ts) uses `parseOrderedSyntax` inputs and existing syntax types, with only tiny fixture-specific facts for known `id` and QName locations. It constructs syntax rather than adding a serializer, compiler or semantic validator. Its nil/content probe and QName resolver examples identify native duties; they do not implement declaration nillability, derivation legality, wildcard processing or scalar facets.

## HTTP shapes and gateway duties

These are actual JSON shape sketches for #410, not generated output or complete XSD lowerings. Existing source-specialized scalar/record schemas remain in place; bag values use their selected scalar schema, or lexical strings for untyped data.

```typescript
type ExpandedName = {namespace: string; local: string};
type AttributeEntry = {name: ExpandedName; value: string};
type MixedParagraph = {
  id: string;
  $content: (string | {name: {namespace: "urn:msg"; local: "b"}; value: string})[];
};
type NilParagraph = null | {
  $nil: true;
  id?: string;
  $attributes?: AttributeEntry[];
  $type?: ExpandedName;
};
type OpenElementValue = {
  $namespaces: Record<string, string>;
  $attributes?: AttributeEntry[];
  $type?: ExpandedName;
} & ({$nil: true} | {$content: (string | {name: ExpandedName; value: OpenElementValue})[]});
```

An OpenAPI/draft-07 mixed record uses `type:object`, required `id` and `$content`, closed properties, and array items `anyOf` string or closed `{name,value}` entry; its known `b` name has constant namespace/local fields. Nil uses `anyOf` null or a closed object requiring `$nil` with `const:true`, admitted attribute/type/context properties, and no content properties. Open records require `$namespaces`, whose values are strings, and recursively permit ordered entries or nil; use native checks for prefix grammar and contextual meaning where the schema is deliberately broader.

HTTP checks enforce JSON fields, types, required properties and useful structural constraints without mutation. Gateway/native checks reconstruct source names/order/grouping, assess scalar facets and lexical witnesses, nil/attribute legality, wildcard strict/lax/skip, QName/type context and SOAP binding/security. A structural superset is allowed only when native checks narrow it before dispatch or response success.

Every accepted field, including `$namespaces`, `$attributes`, `$type` and mixed strings, must survive actual HTTP serialization. #410/#197/#198 must extend existing `componentShape.ts` lowerings and route-local validation; #200 must use a preserving serializer or the existing validated JSON stringify fallback. OpenAPI XML annotations cannot supply these runtime responsibilities.
