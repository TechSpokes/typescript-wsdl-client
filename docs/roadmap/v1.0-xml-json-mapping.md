## Selected keyed mapping contract

Names are JSON keys. Derive identity facts from the exact source mapping whenever a slot uniquely identifies them, including qualified attributes inside a fallback channel. Known records/scalars/arrays and reconstructible application groups remain ordinary values; source occurrence bounds choose arrays for compact slots, while each ordered entry is exactly one element occurrence. JSON property insertion order never controls source-fixed XML order. Existing scalar encodings, lexical witnesses and native duties remain authoritative.

Relative to the primary-source comparisons below, keyed child entries keep familiar field names, text objects make every ordered entry an object without a kind discriminator, direct URI holders handle actual identity choices, and scoped binding deltas avoid repeated full maps. Attribute entries preserve same-name/different-namespace identities without inventing a key-escaping syntax. This selects one concrete extension rather than adopting a dependency's general XML-tree format; existing supported projections do not acquire redundant descriptors.

### Content and recursion

New mixed/open `$content` is an ordered array of objects. Each object has exactly one own property: either `$value` with a text string, or an ordinary child-name key whose value follows that child's selected mapping. No metadata siblings are allowed on an outer entry. Preserve significant spaces; coalesce adjacent text entries and remove zero-length text entries. Do not collapse repeated occurrences across intervening text. An XSD list scalar array is distinct from element repetitions.

```xml
<p xmlns="urn:msg" id="7">Hello <b>world</b>!</p>
```

```json
{"id":"7","$content":[{"$value":"Hello "},{"b":"world"},{"$value":"!"}]}
```

Here the source declares b as string. A mixed structured b instead has its own `$content`, even when one instance is text-only. Source identity/assessment selects the grammar, not object appearance. Metadata around a scalar encoding v uses a holder with `$value:v`, including object/array scalar encodings; never merge scalar fields into element metadata. A record keeps its own fields. An ordered holder cannot also expose peer child/group fields or a scalar `$value`; source-mapped attributes may accompany it.

### Namespaces have separate owners

`$namespace` is the actual element/attribute/type namespace URI at this location. It does not declare a prefix, set a default binding or cause descendants to inherit element identity. Derive it when the exact source mapping fixes identity; otherwise supply it explicitly, including an empty URI for a no-namespace unknown element. Each child key is its XML name without the prefix unless an established source mapping defines an application alias.

```json
{"$content":[{"code":{"$namespace":"urn:vendor","$value":"A"}},{"code":{"$namespace":"urn:billing","$value":"B"}}]}
```

`$namespaces` contains prefix bindings introduced/rebound on this node. Descendants inherit an immutable effective context and apply their local changes; parents and siblings stay unchanged. The first source-defined retained-context boundary captures otherwise unavailable effective bindings; subsequent nodes retain only deltas. A source-known intermediate node retains a delta when a descendant needs it. Prefix keys are data: `""` denotes the default binding and xml is implicit. Default reset uses `{"":""}`; XML Namespaces 1.0 does not permit deleting nonempty prefixes. Redundant deltas normalize away; apparently unused bindings in unassessed data are not pruned.

Element identity and default binding can differ: `<e:extra xmlns:e="urn:open" xmlns="urn:values">Thing</e:extra>` identifies the element in urn:open while a typed QName Thing resolves in urn:values. A child rebinding p changes its applicable lexical scope, not its element URI. Plain unassessed `p:Thing` remains a string; neither object appearance nor a colon grants QName semantics.

For assessed data without retained context, the codec can allocate compatible prefixes from actual identities. It must preserve protected effective contexts for unassessed lexical data and lexical witnesses. Reject combinations that cannot coexist in XML, including a no-namespace element retaining a nonempty default or a namespaced attribute lacking an available nonempty prefix in a protected scope. JSON shape alone does not establish these codec duties. Fresh reconstruction uses complete JSON, source mapping and inherited context; arbitrary extracted-subtree portability is not promised.

### Attribute channel

Existing unambiguous source-mapped peer attributes retain their shape. When a source mapping requires the new fallback, `$attributes` is an array of one-name entries, not an array of generic name/value descriptors. At a uniquely mapped key, a bare scalar derives its complete identity from that source slot, including a qualified namespace; redundant identity holders are rejected.

A closed source with one qualified code attribute and one code child can therefore use `{"$attributes":[{"code":"attribute"}],"code":"child"}`. For an open/unresolved key without a unique mapped identity, a bare scalar denotes an unqualified attribute and a qualified identity uses `{$namespace:nonemptyURI,$value:scalar}`. Empty-URI holders are rejected in that open grammar rather than being a second spelling.

A source key whose permitted identities remain ambiguous requires the explicit namespace selection needed to distinguish them; its generated mapping/schema declares that domain. Unknown attributes retain lexical strings; typed values use their selected scalar encodings. The bag never infers attribute identity from the default element namespace.

```json
{"$attributes":[{"id":"attribute"},{"id":{"$namespace":"urn:vendor","$value":"external"}}],"id":"child"}
```

The container preserves two attributes with the same name from different namespaces without inventing escaping rules or aliases. Source-owned slot attribution determines whether an identity is already fixed; object appearance does not override that attribution. Attribute order is not semantic; canonical output sorts by expanded identity. Duplicate expanded attributes, duplicate peer/bag identities, undeclared attributes and invalid values fail. A selected type uses one placement consistently across nil/non-nil instances. No attribute holder owns children, `$nil` or `$type`.

### Open values, type and nil

Genuinely unassessed elements always use ordered holders, including empty/text-only instances, with their required identity and retained context. They do not become guessed scalar types. Native assessment applies independently to each location: strict/lax/skip cannot be selected by a JSON flag. Raw unassessed xsi:nil/xsi:type stay lexical attributes in the XSI namespace, not semantic `$nil`/`$type`. Missing declarations are not repaired by an open representation.

`$type` is a flat XML identity `{$name:"Dog",$namespace:"urn:animals"}`. `$name` is a string inside an identity value; a child entry already has its name as its key. No `$localName`, `$kind`, `$text` or `$element` alias is allocated. Display type/schema aliases do not rename the selected XML type. Native existence/derivation/attribute duties still apply.

The explicit nil contract below remains authoritative. Identity/type/context metadata can accompany nil only when that exact source mapping declares the necessary combination and implements its native duties; it is not admitted by the nil marker alone. Nil forbids every text/child/group content field, even empty content. Neither semantic xsi processing nor QName scalar assessment is guessed from familiar names.

### Compatibility, HTTP shape and implementation proof

New grammar selection is per exact source declaration/type/assessment mapping. Legacy, accepted component scalar/record/array/simple/ordered values and checkedDirectRuntimeV1 remain unchanged. A reused already-accepted ordered descendant inside a new mixed parent retains its old entry grammar in both directions; the implementation dispatches through its existing mapping. Unifying those old public shapes requires a separate migration decision, not a new mode introduced here.

HTTP schemas describe actual JSON fields and source-selected recursive alternatives, with closed one-property entries, text string slots, namespace strings, flat type identity and nil/attribute/content exclusions. Named structured choice alternatives reference their union, or an array of it for repetition. Use oneOf only where JSON alternatives are disjoint. Native owners enforce names, bindings, particles/correlation, scalar/default/fixed/type/nil duties and SOAP construction. Serialization must independently preserve every accepted field. Reject unknown metadata and invalid combinations without mutation, coercion, default insertion or field removal; legal __proto__/constructor names remain safe own data properties.

They are not a generic source-to-DTO generator or production native validation; existing native projection/scalar controls and nil examples remain separate evidence. The old public candidate grammar is historical; its fixture-specific conversion helpers remain dependencies of the research adapter, not an independent new inverse.

Production consumers are #409 (mixed/namespace/open projection/codec), #421 (nil), #422 (scalar/context), and #410 (actual HTTP schemas/serialization). ## Selected nil contract for the next implementation slice

The maintainer selected one explicit nil object on November 3, 2026. This section supersedes the historical candidate's null shorthand for newly supported component nil values; it does not change legacy, accepted non-nil component values or `checkedDirectRuntimeV1`. The [checked nil reference](../checked-gateway.md#nil-values) records #421's implemented domain and execution evidence; the examples in this research packet retain their narrower proof limits.

| Case | JSON rule |
|---|---|
| Absent optional element | Omit its property; omission is not nil |
| Present nil without attributes | `{"$nil":true}` |
| Present nil with attributes | `{"$nil":true,"id":"7"}` for an applicable mapped string attribute `id` |
| Empty non-nil | Retain the ordinary source-selected value, such as `""`, `{"$value":""}` or an empty permitted record |
| Nil repeated item | Put the explicit nil object at that item's position in the declared array |
| Nil wrapper | Put the explicit nil object at the wrapper element's property; it contains no items |

Both accepted input and canonical output use the explicit object; plain `null` is rejected, including as an array item. `$nil` is exactly Boolean `true`, never false, a string or a caller-selected assessment policy. XML `xsi:nil="true"` and `"1"` project to this same marker after native lexical assessment. XML false/zero uses the ordinary non-nil projection with no `$nil`; reconstruction of nil uses a permitted canonical true lexical form. Property order does not control XML order.

The only newly allocated nil metadata is `$nil`. Additional fields are exactly the applicable attribute properties already defined by the selected source mapping, using their existing scalar encodings and identities. Required attributes remain required on nil elements; optional/default/fixed attributes follow the shared native assessment and adopted augmentation rules, not Ajv defaults. Empty string attributes are data and remain subject to their type. Do not invent a new nil attribute bag or rename existing scalar descriptors. Contextual attribute families, attribute collisions/wildcards and dynamic types require their actual native owners and an explicit compatible shape before emission; the nil marker alone does not establish those capabilities or silently narrow #421's acceptance.

Nil objects prohibit all element/text/group content fields, including `$value`, `$content`, synthetic choice containers and ordinary child properties, even when their supplied values are empty or null. Reject unknown metadata, undeclared/invalid attributes, sparse/malformed arrays and object/array substitutions without mutation or silent field removal. `$type` and `$namespaces` are not implicitly accepted by this nil contract. A later independently selected contextual/type contract must explicitly describe its combination with nil; callers cannot enable it with extra keys.

Each object's XML element identity comes from its selected declaration/position; `$nil` never emits an XML child. Nillability, nil/content legality, attribute use and applicable fixed/default/scalar duties remain native checks, at the actual item or wrapper element. Genuinely unassessed lexical xsi attributes are not promoted to semantic nil by familiar spelling. No checked failure may fall back to legacy conversion, and no missing native duty may be hidden by weakening validation.

For the example with optional string attribute `id`, TypeScript is `{ $nil: true; id?: string }`. Its HTTP schema is concrete:

```json
{"type":"object","required":["$nil"],"additionalProperties":false,"properties":{"$nil":{"const":true},"id":{"type":"string"}}}
```

Include `id` in `required` where the source requires it. Compose this nil schema with the ordinary non-nil schema for a nillable element, with exactly-one composition only when the JSON alternatives are disjoint. Optionality belongs to the containing property and item versus wrapper nillability belongs to the corresponding element position. Every accepted attribute must survive response serialization; HTTP structure validation does not replace native XML checks. No discriminator, response envelope or new runtime mode is introduced.

The [explicit nil contract examples](../../test/research/xml-json-mapping/nil-contract.test.ts) exercise independent hand JSON, true/one XML lexicals, attribute-preserving fresh syntax reconstruction, canonical explicit output, absent/empty/item/wrapper distinctions and malformed combinations. They reuse the existing parser and research inverse for a fixture with string `id`; they do not implement native nillability, complete attribute semantics or generated HTTP/SOAP execution. The old null-based tests remain historical candidate evidence, not accepted aliases.

The #421 implementation consumes this exact contract through existing source planning, projection/inverse, codec and componentShape seams, preserving shared resource/path/error boundaries. Its [codec controls](../../test/unit/direct-projection-nil.test.ts) and [installed gateway qualification](../../test/helpers/checkedGatewayInstalledProcess.ts) supply independent request/response/fault, serialized HTTP and owned-SOAP evidence, including non-nillable/content-bearing refusals and attribute/default/fixed duties. General groups/default names #431 and aliases #432 remain separate. Close #421 only after its reviewed implementation merges; #420's bounded representation acceptance is separate.

## Constraints before syntax

The problem is to expose usable application JSON from a selected service contract while retaining enough information to construct an equivalent permitted XML value from fresh JSON. XML syntax trees, compiled service metadata and application JSON serve different purposes; an internal compiler record is not automatically a suitable public shape.

First identify the declaration and native assessment applicable at each location, including genuinely unassessed content. Then identify which observable facts may vary between permitted instances and cannot be recovered from that contract. Only those facts require an application choice or extra representation information; exact field spelling is a subsequent design choice.

### Obligations and degrees of freedom

| Obligation | Counterexample if omitted | Where enforced | What it does not prescribe |
|---|---|---|---|
| Retain actual order where it varies | `a,b,a` and `a,a,b` collapse to the same grouped properties | Representation and inverse; native language check | `{name,value}` entry objects |
| Retain mixed text positions and spaces | `Hello b !` and `Hello ! b` collapse after concatenation | Representation and inverse | Bare strings versus explicit text entries |
| Identify selected children unambiguously | Two allowed namespaces use the same local name | Source mapping plus necessary instance selection | Full namespace URI on every known child |
| Distinguish attribute and element roles | Attribute `id=7` and child `id=7` flatten identically | Source mapping or explicit channel | A universal attribute array |
| Preserve presence and nil with attributes | Absent, empty and nil collapse; nil attributes disappear into null | Representation plus native nillability/attribute checks | `$nil` spelling or universal null use |
| Recurse under the correct declaration | Identical child names in different parents have different types | Existing source-owned mapping and recursive codec | A global QName-to-shape table |
| Preserve exact scalar meanings | Large integers round; Boolean strings gain guessed meaning | Shared scalar owner | New scalar policies in this issue |
| Preserve required lexical witnesses | Value-equivalent text violates a lexical facet after rewriting | Shared scalar owner | Value equality as permission to discard lexical context |
| Preserve typed QName meaning | Prefix rebinding changes the referenced identity | Native scalar/context owner | Treating arbitrary colon strings as names |
| Preserve unassessed lexical context | Unknown application text changes meaning after prefix pruning | Native assessment selection plus retained context | Interpreting xsi attributes without assessment |
| Keep representation and validity separate | Structurally well-formed JSON encodes a forbidden particle sequence | HTTP structure, then existing native constraints | Recreating an XSD engine in OpenAPI |
| Preserve accepted data through serialization | A serializer drops metadata or a nested field | HTTP response integration | Successful JSON validation as proof of preservation |
| Keep the grammar source-selected | Empty mixed content triggers an undocumented alternate encoding | Mapping selection before instance conversion | One runtime type for nil, unions or permitted polymorphism |
| Preserve existing consumers deliberately | A generated client interprets changed fields incorrectly | Compatibility analysis and migration decision | Treating every existing design as correct forever |

The minimum correctness claim is contract-relative: two observably different permitted XML values under the same contract cannot share identical JSON and both be recovered by a deterministic inverse. ADR-003 may expressly normalize a difference away; source constants can eliminate redundant fields but cannot recover a discarded instance choice. A fresh inverse may use the compiled service contract, without cached original XML, object identity, property insertion order or inferred business meaning.

The reverse direction must reject conflicting, unknown or invalid inputs rather than manufacture a valid XML value by dropping fields or coercing values. Native assessment still establishes legality; a representation prototype alone does not establish that its XML examples are valid under every possible source contract.

### Semantic constraints are not field names

For a fixed source sequence `a,b`, order is known and ordinary properties can suffice. For a repeated choice admitting `a,b,a` and `a,a,b`, the particular sequence is instance data and must survive. Even there, requiring an ordered selection does not require naming its fields `name` and `value`.

A source permitting `(a,b)` or `(c,d)` is straightforward to represent as a union of two closed objects: one requires `a,b`, the other `c,d`. Independent per-property bounds would lose the correlation, but that is a defect of that lowering, not a limitation of JSON Schema. Do not use this simple example as justification for a generic XML-node representation or native-only HTTP constraints.

### Gateway objects are application abstractions

The maintainer explicitly clarified that the SOAP implementation sits behind the gateway API abstraction. Public objects and generated types may group source sequences and choices without corresponding to XML element wrappers. Reuse the existing source mapping and codec to translate those groups; no new compiler or architecture layer is needed.

For the example, the public request can be either of these independently authored values:

```json
{"$choice":{"a":"one","b":"two"}}
```

```json
{"$choice":{"c":"three","d":"four"}}
```

An illustrative schema for string-valued children expresses the choice directly:

```json
{
  "type":"object",
  "required":["$choice"],
  "additionalProperties":false,
  "properties":{
    "$choice":{
      "oneOf":[
        {"type":"object","required":["a","b"],"additionalProperties":false,"properties":{"a":{"type":"string"},"b":{"type":"string"}}},
        {"type":"object","required":["c","d"],"additionalProperties":false,"properties":{"c":{"type":"string"},"d":{"type":"string"}}}
      ]
    }
  }
}
```

The gateway maps `$choice` to the source choice, emits `a` then `b` or `c` then `d`, and adds no XML wrapper for the synthetic group. The `$` prefix keeps the application-only property separate from a real XML child named `choice`; see the [reserved mapping-key inventory](../concepts.md#reserved-mapping-keys). It reconstructs declared namespace identities and order from the contract rather than JSON property insertion order; a mixed branch such as `a,d` fails the schema without a new discriminator or a public `{name,value}` wrapper.

The inline objects above explain the constraint only. The executable prototype also provides named alternative schemas/types, a named union and direct-versus-array references; see [choice groups and named alternatives](../concepts.md#choice-groups-and-named-alternatives) for cardinality, contextual naming and unresolved collision rules.

The group names and types must be generated deterministically with an explained mapping. Nesting and repeated groups use the same recursive source-derived abstractions where their realizations can be reconstructed; ADR-003 normalization still governs invisible grouping rather than promising to preserve grouping history absent from XML. Supplemental native scalar and source duties remain, but must not become an excuse to omit readily expressible JSON structure.

The naming design must also support [configured application names](../concepts.md#configured-application-names) for synthetic group properties, union types/schemas and individual alternatives. Overrides target source identities and must drive matching API artifacts and adapters without renaming the source XML or changing its constraints; the configuration API and executable override behavior remain future integration work.

Namespaces have the same distinction: the namespace of a unique declared child is source metadata, while the selected identity of a genuinely dynamic child is instance information. Explicit expanded names are an internal semantic identity; their object layout is not itself a requirement on all public JSON.

Recursion must be stated as a grammar: a child has its own scalar or structured value under its own declaration, and the same rules apply at every depth. The previous prototype's fixture-name predicates illustrate a few cases only; they are not a source-derived recursive mapping proof, especially for the same QName in different containing declarations.

### Contract-relative inverse requirements

For one selected native contract, the XML domain is its permitted values within the declared implemented assessment scope, and the JSON domain is the corresponding admitted application representations. Define projection from XML to JSON and reconstruction from fresh JSON to XML against that same contract; neither function may choose a broader assessment policy to make an input succeed.

Every XML value in the declared domain needs a defined projection; otherwise the capability boundary must explicitly exclude it. Every admitted JSON value needs a fresh reconstruction whose native assessment succeeds within that same declared scope. The laws below apply to those domains, not all well-formed XML or arbitrary JSON.

```text
reconstruct(project(xml), contract) is equivalent to xml under ADR-003
project(reconstruct(json, contract), contract) equals normalize(json, contract)
normalize(normalize(json, contract), contract) equals normalize(json, contract)
```

Equivalence and normalization must identify the permitted differences before running those laws: default/fixed augmentation, scalar lexical representatives, invisible grouping and significant text follow the existing native owners. Declare malformed representation inputs separately from native-invalid values and unsupported capabilities; a failure in one class cannot become successful conversion in another class.

The context needed by reconstruction is the exact declaration/type and particle position selected by the existing native mapping, not a table keyed by element name or parent name. For example, identical `row/value` names under different ancestor declarations can require integer versus QName values even though the immediate parent QName is identical. In `(a|b)*`, both identities are known from source, but the instance must still identify the selected alternative at every occurrence; source-known identity does not mean source-determined selection.

Assessment is also per applicable element and attribute, not one Boolean property of a whole subtree. An assessed record can contain a declared QName attribute, an unassessed wildcard attribute and child wildcards with different policies; the representation must preserve the information needed by each owner without treating a native-invalid value as unassessed. The prototype's global flags do not establish this general case.

The inverse therefore needs the existing native declaration/type attribution, the current particle alternative/occurrence, applicable attribute uses and scalar descriptors, effective type selection where supported, and namespace/lexical context where consumed. These are inputs from existing mapping and assessment owners, not a new public plan or another validation layer. Object appearance cannot replace them: a typed QName object and a business record with `namespace` and `local` children can have identical JSON structure and different meanings.

### Explicitly excluded requirements

ADR-003 excludes original bytes, prefix spelling for assessed names, comments, processing instructions and CDATA segmentation from adopted equivalence. Preserve significant mixed spaces, exact scalar meaning, necessary lexical witnesses and unassessed namespace bindings; these exclusions do not authorize discarding them.

Do not invent invisible group history when different groupings yield the same observable XML. SOAP encoded identity graphs and signed original bytes remain at their existing separate owners. This analysis cannot change source admission, nil/type validation or published direct-runtime guarantees by choosing a convenient JSON syntax.

### Competing grammars to challenge

No complete replacement grammar is selected here. The maintainer-directed starting point for known structure is source-derived application groups; any residual mixed/open representation must justify its remaining fields against that abstraction. The current form, property-keyed entries and explicit metadata-node entries remain comparison cases, not constraints on the public API.

| Candidate family | Representative entry | Strongest reason to consider it | Required challenge |
|---|---|---|---|
| Source-derived application groups | `{$choice:{a,b}}` or `{$choice:{c,d}}` | Direct recursive sequence/choice abstractions and ordinary schema composition | Deterministic naming/mapping, repeated/nested groups, normalization and compatibility |
| Current generic entries | `{name:{namespace,local},value}` | Existing component implementation and direct identity | Exposed metadata, redundant source facts, overloaded `value`, mixed string/object grammar |
| Property-keyed entries | `{b:childValue}` and `{$value:text}` | Familiar XML names and existing reserved text convention | Exact one-member rule, namespace collisions, dynamic names, source-specific typing, compatibility |
| Explicit metadata nodes | `{$element:identity,$content:[...]}` | Visible node role and recursive structure | Extra wrappers, unnecessary identities, ordinary-data ergonomics, compatibility |

Object-versus-string discrimination is mechanically possible in the current grammar, but that does not establish human readability. Uniform objects do not establish simplicity either: count semantic rules, exceptional cases and the work needed to understand or author a nested value, rather than merely counting keys or bytes.

Use the same complete XML examples for all candidates: ordinary fixed records, variable interleaving, nested mixed content, namespace and role collisions, nil items/wrappers/attributes, exact scalars, contextual QNames and unassessed values. Each must show an independent fresh JSON inverse and rejection of malformed variants, with no silent change to the accepted contract domain.

Require an explicit common source contract admitting both XML instances before claiming a counterexample disproves reversibility for that contract. The syntax-only examples in `constraints.test.ts` identify potential information losses and a controlled wrapper-free sequence; they neither establish source legality nor qualify any full candidate grammar. Source-backed native controls must carry the corresponding declaration and particle obligations into candidate comparison.

Challenge every repeated identity field by removing it and asking whether the complete source state and remaining JSON still reconstruct the same instance selection. For opaque values, challenge every omitted binding by exhibiting application text that could depend on it. Equally preserving candidates need comparison through concrete authoring, inspection, TypeScript narrowing, HTTP-schema and error-reporting tasks; field counts alone cannot choose the more understandable interface.

Complete namespace maps repeated on every opaque element are sufficient, not proven necessary: compare inherited bindings plus local declarations/undeclarations against full maps using fresh reconstruction, rebinding and independent subtree requirements. Likewise, compare one explicit nil form against accepting both null and a metadata object; preserving nil attributes does not itself require two spellings. No proposed simplification may silently change an already accepted source/consumer contract.

The property-keyed candidate must reject entry wrappers containing two children without imposing that one-member rule on the child value itself. It must separately handle two known namespace-colliding names, truly dynamic names, absent/null/empty values and safe own `__proto__`/`constructor` keys. Define text-entry versus element-value positions and duplicate JSON member handling at the HTTP parsing boundary; duplicates lost by ordinary `JSON.parse` cannot be detected by a later object-only validator, and the same limitation must be audited for every candidate.

Compatibility evidence must distinguish introduced implementation, accepted contract, generated shape, artifact compatibility and published behavior. Existing code is not proof of optimal public design, and failure to find external consumers is not permission to alter an accepted contract. No compatibility change is authorized by this comparison alone.

### What previous evidence establishes

The original tests show that particular examples survive the implemented representation and that several malformed forms fail. They do not establish minimal metadata, the best public grammar, a complete recursive source mapping, stronger native capability support, or that alternatives are less usable.

The existing `{name,value}` public emission was introduced in commit `1c6caac3969d72aa1c6b5d33d537f73a734bd18c`: `directValues.ts` copies the source element identity into `name`, and `componentShape.ts` exposes that wrapper in generated TypeScript and HTTP schemas. This implementation provenance explains the convention's existence; it is not evidence of a separately justified requirement for those exact public fields. Actual consumer and artifact compatibility must be investigated before changing it, while design quality remains open to challenge.

## Classification before representation

### Backward actual-chain experiment

The maintainer proposed starting at the final definition and following its actual base links. The bounded [experiment](../../test/research/xml-json-mapping/backward-derivation.test.ts) implements that traversal independently of the existing forward composer, using the parsed/resolved canonical graph. It does not construct a reordered hypothetical ancestry or issue native source-validity receipts.

The [research source](../../test/research/xml-json-mapping/derivation-chain.xsd) defines a customer with required `Name` and optional `Phone`, restricts it to `Name`, then extends it with required `Email`. Starting at `WithEmail`, the experiment visits `WithEmail`, `NoPhone`, `Customer`, and reconstructs exactly `Name,Email`; unrelated sibling extensions do not enter the result.

At an extension, prepend the older retained content before the newer contribution. At a restriction, retain its replacement content and stop inheriting older child content, even when the replacement is empty. Continue following bases to compute attribute decisions: omitted attributes can remain inherited, while a newer prohibition must suppress an older optional declaration; separate legality checks still consume the retained source graph.

Four tests pass with independent expected observations and comparisons against the existing composer: ordinary restriction/extension, empty restriction followed by addition, removal of optional string `a` followed by required integer `a`, and an invalid required-attribute prohibition. In the invalid control, backward computation produces a prohibition while the existing composition check rejects it; this does not disprove backward traversal, but demonstrates why computation must retain applicable validation duties.

These observations support backward traversal for the experiment's actual complex-content chains. The code explicitly excludes mixed/simple content, attribute groups/wildcards and explicit builtin bases; it preserves particle identities rather than replacing grammar with a flat field dictionary. Attribute observations retain local name/use/default lexical value only, not a full typed attribute plan; no attribute-plan equivalence is claimed. The experiment establishes neither full XSD legality nor a complete RE01 reordered-witness procedure, and supplies no counterexample to a backward algorithm that correctly applies all required checks.

`name` and scalar QName objects have exactly `namespace` and `local`, both strings; `local` is an XML NCName. ### Allowed combinations and rejection

Non-nil assessed values use exactly their source-selected content form: ordinary child properties, `$value`, or `$content`, even when one instance is empty or text-only. A mixed/ordered record cannot also contain ordinary child properties or `$value`; known peer attributes, `$attributes`, `$type` and required `$namespaces` may accompany its content. Existing simple-content records may combine their `$value` with accepted peer attributes; new colliding/open attributes use the bag.

Nil uses `null` or an object with `$nil:true` plus attributes, `$type` and required `$namespaces`; no `$value`, `$content` (even empty), or ordinary child property is allowed. `{$nil:true}` is accepted as an attribute-free spelling and canonicalizes to `null`; `$nil:false` is rejected in JSON. On XML input, `xsi:nil="false"` or `"0"` is ordinary non-nil and the marker normalizes away.

Reject unknown metadata, missing entry members, extra entry members, invalid names, duplicate expanded attributes, undeclared peer fields and conflicting channels before returning a reconstructed value. Namespace declarations cannot masquerade as application bag attributes; interpreted `xsi:nil`/`xsi:type` use semantic metadata instead of a duplicate bag channel. No unknown `$` field becomes an XML child, and no validator silently removes fields, coerces values or mutates inputs.

Legal XML names `__proto__` and `constructor` are ordinary identities, not reserved metadata. Use safe own-property construction for any name-keyed native structures; the prototype preserves these names in expanded entries without assigning them to object prototypes. This does not change current source/bootstrap admission gates or reserve those XML names globally.

### Presence and nil examples

An absent optional child is omitted from its record or ordered sequence. An empty non-nil string element is `""`, an empty ordinary complex value is `{}` where the selected contract permits it, and an empty ordered complex value is `{"$content":[]}`; the source distinguishes these contracts.


```json
{"id":"7","$nil":true}
```

The fixture's unqualified `id` remains a source-known peer. A separate qualified `a:id` is `{"name":{"namespace":"urn:attr","local":"id"},"value":"qualified"}` inside `$attributes`; the default element namespace never qualifies unprefixed attributes.

In a simple-content record array, `[null,{"$value":""},{"$nil":true,"id":"7"}]` denotes three item elements; a scalar-string item contract instead uses `""` for its empty non-nil item. A wrapper value of `null` denotes one nil wrapper, with no item content; an absent wrapper is omitted. #421 must apply nillability, required/allowed attributes, fixed/default and nil-content constraints at each actual element, never to an array as a surrogate for its wrapper.

### Namespace and contextual scalar rules

A declared QName scalar uses the ADR's expanded `{namespace,local}` value; attributes or simple-content wrappers retain the selected scalar position. `p:T` and `alias:T` are equal only when both resolve to the same namespace; a child rebinding `p` changes the expanded value. A string such as `unbound:T` remains that string, without resolution or guessed semantics.

For genuinely untyped lax/skip subtrees, retain a complete effective namespace map on every element, including inherited bindings, unused bindings and nested rebindings. Retain the default binding when present; `"":""` records a default undeclaration, while `xml` is implicit and omitted canonically. A fresh inverse needs no parent/source XML to interpret the map; it must not change or prune an original binding based on colon heuristics.

Native assessment determines whether a node's xsi attributes were interpreted; the JSON caller cannot select that status. On genuinely unassessed skip data, retain `xsi:nil` and `xsi:type` as lexical `$attributes` entries, including false/invalid-looking nil strings, unbound colon strings and content beside a raw nil attribute; do not synthesize semantic `$nil`/`$type`, infer a typed QName from a familiar element name, or promote a familiar attribute to a peer. The [wildcard processing rules](https://www.w3.org/TR/xmlschema-1/#Wildcard_details) distinguish skip's well-formedness requirement from assessed values; the native owner must determine the exact lax assessment outcome, including available declarations/types, before selecting this unassessed representation.

Unassessed values require `$namespaces` and `$content` plus optional lexical `$attributes`; `null`, `$nil`, `$type` and `$value` are rejected at those locations. An assessed element may separately require retained context for genuinely untyped lexical data within it; its interpreted xsi values use semantic metadata. These are source assessment facts, not a new public discriminator, mode or validation opt-out.

Prefixes must be NCNames except the empty default key; reject `xmlns`, invalid `xml` bindings, bindings to the xmlns namespace, and empty URIs for nonempty prefixes. Expanded typed QNames reuse a compatible existing binding deterministically (sorted prefix order) before generating a prefix that avoids every retained key; repeated normalization must not grow the scope. No-namespace QName lexical output requires an empty default namespace; incompatible retained context is rejected rather than rebound.

`$type` records explicit expanded `xsi:type` identity, including an explicitly supplied declared type; it does not prove that type exists or is a permitted derivation. #409/#422 must preserve scalar context and lexical witnesses and perform native dynamic-type duties before admitting this currently refused capability. The prototype resolves QName meaning through the existing `resolveLexicalQName`; an unbound typed QName failure is a native scalar duty, not evidence that all colon strings are malformed JSON.

### Construction and normalization

Forward construction starts with the selected source projection and existing scalar assessment. Keep ordinary records, arrays, Boolean values, int32 numbers, precision-sensitive decimal/integer strings and existing `$value` unchanged; never convert exact scalars through JavaScript `Number`. Source-known uniquely inferable grouping remains reconstructed by the existing projection.

For mixed/variable/open content, visit ordered syntax, append text strings and existing element entries, and preserve significant spaces, nesting and multiplicity. Extract assessed nil and type into their metadata positions, put uniquely mapped known attributes in peers, and put remaining permitted attributes in the expanded bag; unassessed data keeps lexical xsi attributes. Retain scopes only where source assessment selects contextual lexical preservation; other known records reject unsolicited `$namespaces`.

The fresh inverse reads only JSON plus the selected source contract, reconstructs names and fixed sequence from that contract, and walks `$content` for actual order. It reconstructs bag attribute identities, nil and typed-QName namespace bindings without reading the original XML. It then hands the fresh native value to the existing scalar/particle/codec owners; no checked failure is routed through legacy conversion.

Canonical normalization coalesces adjacent text strings, removes zero-length text entries, preserves every significant space, sorts attribute entries by expanded identity, and ignores attribute order. Empty text and CDATA segmentation, comments, processing instructions, prefix aliases, entity spellings, nil false markers and original bytes are outside the adopted equivalence. Unknown lexical application strings and retained bindings remain unchanged.

Schema-defined default/fixed augmentation remains at native assessment; absent required elements are never invented. Lexical-sensitive facets still require a retained admitted witness or justified shared normalization. Invisible group history and empty realizations follow ADR-003's existing canonical representative, not new JSON group tags.

## HTTP shapes and gateway duties

These are historical candidate JSON shape sketches for comparison, not finalized #410 handoffs, generated output or complete XSD lowerings. Existing source-specialized scalar/record schemas remain in place; bag values use their candidate scalar schema, or lexical strings for untyped data.

```typescript
type ExpandedName = {namespace: string; local: string};
type AttributeEntry = {name: ExpandedName; value: string};
type MixedParagraph = {
  id: string;
  $content: (string | {name: {namespace: "urn:msg"; local: "b"}; value: string})[];
};
type NilParagraph = null | {
  $nil: true;
  id?: string;
  $attributes?: AttributeEntry[];
  $type?: ExpandedName;
};
type OpenElementValue = {
  $namespaces: Record<string, string>;
  $attributes?: AttributeEntry[];
  $content: (string | {name: ExpandedName; value: OpenElementValue})[];
};
```

An OpenAPI/draft-07 mixed record uses `type:object`, required `id` and `$content`, closed properties, and array items `anyOf` string or closed `{name,value}` entry; its known `b` name has constant namespace/local fields. Assessed nil uses `anyOf` null or a closed object requiring `$nil` with `const:true`, admitted attribute/type/context properties, and no content properties. Unassessed open records require `$namespaces` and `$content`, optionally lexical `$attributes`, and recursively contain open entries; use native checks for prefix grammar and contextual meaning where the schema is deliberately broader.

HTTP checks enforce JSON fields, types, required properties and useful structural constraints without mutation. Gateway/native checks reconstruct source names/order/grouping, assess scalar facets and lexical witnesses, nil/attribute legality, wildcard strict/lax/skip, QName/type context and SOAP binding/security. A structural superset is allowed only when native checks narrow it before dispatch or response success.

Every accepted field, including `$namespaces`, `$attributes`, `$type` and mixed strings, must survive actual HTTP serialization. #410/#197/#198 must extend existing `componentShape.ts` lowerings and route-local validation; #200 must use a preserving serializer or the existing validated JSON stringify fallback. OpenAPI XML annotations cannot supply these runtime responsibilities.
