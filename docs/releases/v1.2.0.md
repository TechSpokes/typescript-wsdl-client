# TypeScript WSDL Client v1.2.0

## Independent services, mapped streams and bounded RPC

Version 1.2.0 combines scoped legacy compilation, native multi-service legacy gateways, stream DTO and transport corrections, and the bounded checked SOAP 1.1 RPC/encoded profile. Existing projects retain legacy generation by default; regeneration has the compatibility impacts below. See the root [README](../../README.md).

## What This Improves

Independent sources can share a discoverable REST API while retaining separate clients, catalogs, endpoints and security. Scoped types survive name collisions, and incremental records use generated DTO mapping. The bounded checked RPC profile executes opaque string exchanges without claiming geographic correctness.

The [current roadmap](../../ROADMAP.md#release-availability-and-upgrade-impact) distinguishes already published capabilities, this candidate's implemented scope and deferred work. Historical plans and broader coverage issues remain separate from this release's acceptance.

## Highlights

### Multi-service gateways and scoped declarations

Use `pipeline --services-config` or `runMultiServicePipeline` to generate independent WSDL clients and service routers behind one typed aggregate gateway and one OpenAPI definition. Service-qualified component references and operation identifiers preserve ownership when services reuse names. Runtime client construction keeps each WSDL, endpoint, credentials and transport settings explicit.

The legacy compiler preserves local declaration identities instead of merging declarations whose generated display names collide. Non-colliding names retain their existing behavior. See the [gateway guide](../gateway-guide.md#multi-service-setup) and [API reference](../api-reference.md#runmultiservicepipeline).

### Incremental legacy responses

Configured NDJSON and JSON-array responses map complete XML records through the existing DTO conversion before delivery. Attribute fields, scalar policies, simple content, XML lists and repeated fields follow generated metadata. Requests reuse node-soap's schema serializer for namespace qualification, and stream calls honor supported endpoint, security, certificate, deadline and cancellation settings.

The Escapia Main and Content proof exposes 17 routes through one gateway and API definition. Six Test-target reads passed, including company and content reads for ABC Rentals (`7007`) and A Perfect Vacation Rental (`1273`); all 21 streamed records validated against the advertised schemas. Vendor requests explicitly disabled array-wrapper flattening. This qualifies those selected reads, not every operation or production.

### Checked RPC/encoded profile

Checked component generation supports the bounded NOAA-style SOAP 1.1 RPC/encoded contract: required typed scalar parts, one flat 73-field Boolean record and one opaque string result. Supported response encodings include verified ISO-8859-1 under the existing encoding-agreement policy. No implicit JavaScript Date or floating-point conversion is introduced.

All 12 NOAA operations have owned-server qualification. The 2026-11-09 live gateway retest succeeded for ten operations. `GmlTimeSeries` and `GmlLatLonList` returned non-SOAP provider responses, including `Not connected : ` after input adjustments, and were correctly refused. See the [NOAA qualification](../noaa-ndfd-qualification.md#all-operation-live-retest-on-2026-11-09).

## Upgrade Notes

Read [1.1.x-to-1.2.0 migration](../migration.md#from-11x-to-120) before installing or regenerating. Published npm starting points include 1.1.5 and 1.1.8; 1.1.6 and 1.1.7 were unpublished candidates, not required intermediate upgrades.

Installing the package does not itself rewrite a gateway, although a consumer's build/install scripts can regenerate it. The existing legacy command remains valid. Native multi-service composition and checked generation are separate opt-in adoptions; checked replies do not use the legacy success envelope.

| Existing project area | Migration impact |
|---|---|
| Colliding declarations | Exported DTO/schema names and stream `recordType` references can change |
| Configured streams | Public records use mapped DTOs instead of lexical attribute bags |
| Upgrade from 1.1.5 | Also includes the Boolean-attribute and simple-content corrections shipped in 1.1.8 |
| App and test customizations | Existing scaffolds are preserved; review updates before force replacement |
| Published 1.1.5 direct clients | Versioned runtime binding retains its original restricted contract |

These corrective changes can require consumer source or JSON-contract updates; the minor version is not a promise of a drop-in regeneration upgrade. Regenerate matched catalogs, clients, metadata helpers, OpenAPI and gateways from original WSDL/XSD sources, then review the diff and run consumer checks. Keep known-working manifests, lockfiles, inputs and artifacts for rollback; an older lossy catalog cannot recover previously merged declarations.

The release skill includes the canonical migration reference and profile-specific construction, dependency and scaffold guidance. Its instructions distinguish retained 1.1.5 direct-runtime compatibility from checked-component regeneration; they do not direct existing projects to adopt a new profile automatically.

Keep Node.js >= 24, ESM and the existing runtime dependencies. A separately maintained generated app needs its own dependency/lockfile update. Checked applications, including hosts using the retained 1.1.5 direct binding, depend on this package at runtime; keep it in production dependencies rather than retaining it only as generator development tooling.

Legacy streaming retains a UTF-8 parser; checked encoding agreement does not broaden it or the narrower direct runtime. Dates remain type-level and bigint gains no JSON convention. Stream memory depends on record size and transport/parser buffering; committed responses truncate on failure.

## Validation

Representative release qualification exercises CLI, composition, streaming and NOAA regressions, a locally packed two-source consumer, independently owned SOAP dispatch, mapped HTTP responses, and the retained published 1.1.5 direct-client compatibility fixtures. Strict TypeScript, conformance, installed-package checks and documentation/skill validation cover their stated boundaries.

The [release candidate PR](https://github.com/TechSpokes/typescript-wsdl-client/pull/464) records the matching final conformance, release-preflight and hosted Node 24/26 results, with generated-consumer and artifact evidence. These checks do not certify migration of every existing project or acceptance of every provider operation. Consumers still need their own build, maintained tests and authorized backend checks; generated mock/scaffold tests alone do not establish that readiness.

## Notes

Target release: `v1.2.0`. This candidate task creates no tag and performs no publication.

One package distributes both legacy and checked profiles; native multi-service composition currently joins legacy-generated routers only. Checked composition and checked incremental decoding remain deferred. General SOAP encoding, encoded arrays/shared graphs, arbitrary RPC records, multiple return values and declared RPC faults remain outside the bounded RPC profile.

Private provider captures, credentials and generated proof projects remain outside the npm package. Package contents retain the generic implementation, declarations, consumer guides and required generation resources. Provider availability is separate from package compatibility; the two live NOAA GML failures remain a disclosed limitation rather than successful live qualification.
